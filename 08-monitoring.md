# Monitoring, Logging & Alerting Interview Handbook

---

# What is Monitoring?

Monitoring is the process of continuously collecting and analyzing metrics, logs, events, and traces from infrastructure and applications to ensure system health, availability, and performance.

Interview Answer:

Monitoring provides visibility into the health of applications, servers, containers, Kubernetes clusters, databases, and cloud resources. Without monitoring, teams only learn about issues after customers report them.

---

# Why Monitoring is Important

Without Monitoring:

```text
Application Down
      ↓
Customer Reports
      ↓
Investigation Starts
```

With Monitoring:

```text
Application Down
      ↓
Alert Generated
      ↓
Team Notified
      ↓
Issue Investigated
```

---

# Three Pillars of Observability

Modern monitoring relies on:

```text
Metrics
Logs
Traces
```

---

# Metrics

Metrics are numerical values collected over time.

Examples:

```text
CPU Usage
Memory Usage
Network Traffic
Request Count
Error Rate
Response Time
```

Interview Answer:

Metrics help identify trends, performance bottlenecks, capacity issues, and infrastructure health.

---

# Logs

Logs are timestamped records generated by applications and systems.

Examples:

```text
INFO
WARN
ERROR
DEBUG
```

Interview Answer:

Logs provide detailed information about what happened inside applications and systems during a specific time period.

---

# Traces

Traces track a request as it travels across multiple services.

Example:

```text
Frontend
 ↓
API Gateway
 ↓
User Service
 ↓
Database
```

Interview Answer:

Tracing helps identify where latency occurs in distributed microservice environments.

# Prometheus

Prometheus is an open-source monitoring system used for collecting and storing metrics.

Interview Answer:

Prometheus periodically scrapes metrics from applications, Kubernetes clusters, servers, and exporters and stores them in a time-series database.

---

# How Prometheus Works

```text
Target
 ↓
Prometheus Scrape
 ↓
Time Series Database
 ↓
Grafana
```

Interview Answer:

Prometheus pulls metrics from configured endpoints at regular intervals rather than waiting for systems to push metrics.

---

# Exporters

Exporters expose metrics in a format Prometheus understands.

Common Exporters:

```text

Nginx Exporter
Blackbox Exporter
```

---

# Node Exporter

Purpose:

Collect Linux server metrics.

Provides:

```text
CPU
Memory
Disk
Network
Load
```

Interview Answer:

Node Exporter is commonly deployed on Linux servers to expose operating system metrics for Prometheus.

---

# Grafana

Grafana is a visualization platform used for dashboards and monitoring.

Interview Answer:

Grafana connects to data sources such as Prometheus and displays metrics through interactive dashboards.

---

# Alerting

Purpose:

Notify teams when thresholds are exceeded.

Example:

```text
CPU > 80%
Disk > 90%
Application Down
```

Interview Answer:

Alerting allows teams to proactively respond to issues before they impact customers.

---

# AlertManager

AlertManager processes alerts generated by Prometheus.

Functions:

```text
Deduplication
Grouping
Routing
Silencing
```

Interview Answer:

AlertManager reduces alert noise and routes notifications to the correct teams.

# ELK Stack

ELK stands for:

```text
Elasticsearch
Logstash
Kibana
```

---

# Elasticsearch

Purpose:

Store and search logs.

Interview Answer:

Elasticsearch indexes logs and allows fast searching across millions of log records.

---

# Logstash

Purpose:

Transform and process logs.

Interview Answer:

Logstash parses, enriches, and routes log data before it is stored.

---

# Kibana

Purpose:

Visualize and search logs.

Interview Answer:

Kibana provides dashboards and powerful search capabilities for investigating application and infrastructure issues.

---

# FluentBit

Purpose:

Collect logs from Kubernetes and servers.

Interview Answer:

FluentBit is lightweight and commonly deployed as a DaemonSet to collect container logs from every Kubernetes node.

---

# Loki

Loki is a lightweight log aggregation system created by Grafana Labs.

Interview Answer:

Loki indexes metadata rather than full log contents, making it cost-effective compared to Elasticsearch for Kubernetes environments.

# SLO

Service Level Objective.

Example:

```text
99.9% Availability
```

Interview Answer:

SLOs define expected service performance targets.

---

# SLA

Interview Answer:

---

# SLI vs SLO vs SLA

Interview Answer:

# Common Incident Investigation Flow

Question:

Application is slow.

Interview Answer:

I start with dashboards to identify abnormal metrics, review infrastructure resource utilization, inspect application logs, analyze database performance, and trace request paths to isolate the bottleneck.

---

# Scenario 1

## CPU Suddenly High

Investigation:

```text
Check Grafana
Check Prometheus Metrics
Check Top Processes
Check Traffic Increase
Review Recent Deployment
```

Interview Answer:

High CPU could be caused by increased traffic, inefficient code, infinite loops, memory pressure, or resource-intensive background jobs.

---

# Scenario 2

## Memory Usage Increasing

Investigation:

```text
Application Metrics
Heap Usage
Container Limits
Recent Releases
```

Interview Answer:

Gradually increasing memory consumption often indicates memory leaks or unbounded caching behavior.

---

# Scenario 3

## Disk Usage Reaches 95%

Investigation:

```text
df -h
du -sh
Log Growth
Backup Files
```

Interview Answer:

Log accumulation is one of the most common causes of disk space issues in production systems.

---

# Scenario 4

## Kubernetes Pods Restarting

Investigation:

```text
kubectl describe pod
kubectl logs
Resource Usage
Events
```

Interview Answer:

Repeated restarts typically indicate application crashes, probe failures, resource exhaustion, or dependency issues.

---

# Scenario 5

## Database Slow

Investigation:

```text
CPU
Memory
Connections
Queries
IOPS
Latency
```

Interview Answer:

Database bottlenecks are often caused by inefficient queries, insufficient indexing, connection exhaustion, or resource saturation.

Always Follow:

```text

 ↓

 ↓
Gather Metrics
 ↓
Review Logs
 ↓
Validate Infrastructure
 ↓
Find Root Cause
 ↓
Apply Fix
 ↓
Monitor Recovery
 ↓
Perform RCA
```

---

# Root Cause Analysis (RCA)

Interview Answer:

An RCA should explain what happened, why it happened, how it was resolved, customer impact, and what preventive actions will avoid recurrence.

---

# What Interviewers Expect

Question:

How do you troubleshoot a production issue?

Strong Answer:

I first determine the scope and severity of the issue. I review dashboards to identify abnormal metrics, inspect logs for application errors, validate infrastructure health, analyze recent deployments, and correlate findings to identify root cause. After service restoration, I perform a root cause analysis and implement preventive measures.
